# 수정된 B&D — 증분 동기화 설계

> 상태: **합의 완료, 미착수**
> 선행 작업(A·C)은 배포 완료. 이 문서는 그다음 단계의 확정 설계다.

## 왜 하는가

경기 1건이 기록되면 **화면을 열어둔 사람 전원이 각자 시즌 전체를 다시 받는다.**
경기가 쌓일수록 한 번의 조회가 무거워지고(제곱 증가), 보는 사람 수만큼 곱해진다.

동호회 저녁 운동 1회 (회원 20명 접속, 50경기 기록) 기준 추정:

| | 하루 저녁 | 월 8회 |
|---|---|---|
| 현재 (A 적용 후) | 50경기 × 20명 × 130KB ≈ 130MB | 약 1GB |
| 수정된 B&D | 20명 × 130KB(첫 로드) ≈ 2.6MB | 약 21MB |

학교(태블릿 1대)보다 **동호인(다수 접속)이 훨씬 무겁다.** 보는 사람 수만큼 곱해지기 때문.
따라서 이 작업의 최대 수혜자는 동호인 리그다.

## 핵심 동작

1. 페이지 열 때 **전체 1회 로드** (현재와 동일)
2. 이후 **경기 추가·RP 변경은 실시간 알림에 담긴 내용으로 즉시 반영** — 조회 0회
3. **경기 삭제·수정은 전체 재조회**로 폴백 (드물고 파급이 크다)

핵심은 "다시 읽지 않는다"이지 "적게 들고 있는다"가 아니다.
손에 든 목록은 **항상 완전한 상태로 유지**되므로 호칭·리벤지·휴면감점이 깨지지 않는다.
(폐기된 D안은 이력을 잘라내서 이 판정들을 망가뜨렸다.)

## 안전장치 — 필수 구성요소

빼면 계획이 성립하지 않는다. 부가 옵션이 아니다.

4. **중복 제거 (경기 ID 기준)** — 자기가 쓴 경기가 알림으로 되돌아온다.
   현재는 전체 재조회가 덮어써서 가려져 있던 문제. 증분에선 바로 터진다.
   거르지 않으면 경기가 2건씩 보이고 승패·연승이 부풀려진다.

5. **저장 직전 경량 확인** — 동시 기록 대비.
   "경기 수 + 마지막 created_at"만 묻는 1줄짜리 조회로 로컬과 대조하고,
   다를 때만 전체를 받아 보너스를 다시 계산한 뒤 저장한다.
   ⚠️ 이 확인을 전체 조회로 하면 절감이 통째로 사라진다. 반드시 경량으로.

6. **안전망: 5분 주기 + 화면 복귀 시 전체 동기화** — 알림 유실 대비.
   조회 1회뿐이라 다수 접속에도 부담 없다.

7. **과거 시즌 조회 중 증분 차단** — 현재 시즌 데이터가 과거 시즌 화면을 오염시키지 않도록.
   현재 코드의 가드는 전체 재조회 경로에만 있다(`isBackground && currentViewSeason !== "현재 시즌"`).
   증분 경로에도 같은 가드가 필요하다.

## 범위 밖 — 건드리지 않는다

8. **예약·도전장·입장 호출** (`scheduled_matches` 경로).
   동호인 UX의 핵심이고 이미 별도의 가벼운 조회로 돌아간다.

9. **RP 계산 로직, 보너스·패널티 규칙, 호칭 판정.**
   이 작업은 *입력 데이터를 확보하는 방식*만 바꾸고 *계산 자체*는 그대로 둔다.
   이 선을 넘으면 위험도가 완전히 달라진다.

## 배포 전 검증 — 로컬 PostgreSQL로 재현

10. 아래 5가지를 실제로 돌려 확인한 뒤 배포한다.
    - **동시 기록 2대** — 5번이 작동해 나중 기기가 최신을 반영하고 계산하는가
    - **알림 유실** — 이벤트를 일부러 버린 뒤 6번이 복구하는가
    - **자기 경기 에코** — 같은 경기가 두 번 들어와도 4번이 걸러내는가
    - **경기 삭제** — 전체 재조회로 폴백하는가
    - **다수 접속** — 연결이 늘어도 조회가 늘지 않는가

## 잠재 리스크

| | 리스크 | 심각도 | 대응 |
|---|---|---|---|
| 1 | 중복 반영 (자기 경기 에코) | 🔴 | 4번 (ID 기준 제거) |
| 2 | 확인 절차가 절감을 되돌림 | 🔴 | 5번을 경량 조회로 설계 |
| 3 | 알림 유실로 목록이 조용히 불완전 | 🟡 | 6번 + 5번이 최종 방어선 |
| 4 | 동시 기록 순서 꼬임 | 🟡 | 5번. 학교는 태블릿 1대라 무관 |
| 5 | 과거 시즌 조회 중 오염 | 🟡 | 7번 |
| 6 | **오류가 조용하다** | 🔴 | 아래 참고 |
| 7 | 코드 복잡도 증가 (증분/전체 두 경로) | 🟢 | 감수 |

**6번이 가장 중요하다.** 이 방식의 실패는 "RP가 3점쯤 이상한데?" 같은 형태로 나타나
몇 주 뒤에야 발견되고 원인 추적이 어렵다. 과거에 겪은 "RP가 미묘하게 틀리던" 문제의
재발 경로가 정확히 여기다.

## 동시 기록에 대한 사실 확인

여러 명이 동시에 기록하는 위험은 **이 작업으로 생기는 것이 아니라 지금도 있다.**
현재도 각 기기는 자기 손에 든 목록으로 보너스를 계산하고, 전체 재조회는 알림이
*온 뒤에* 일어나므로 그 사이 틈이 열려 있다. 게다가 지금은 저장 직전 확인이 아예 없다.

수정된 B&D는 이를 두 가지로 개선한다.
- 반영이 더 빠르다 (알림 → 즉시 갱신. 서버 왕복이 빠진다)
- 5번(저장 직전 확인)이 **지금 없는 안전장치를 새로 추가한다**

## 배경 — 왜 전체 재조회 구조가 생겼나

```
players.win_count / lose_count 를 아무도 갱신하지 않았다
        ↓
DB의 승패 합계를 신뢰할 수 없어, 클라이언트가 시즌 전체 경기를 받아 직접 셌다
        ↓
순위표를 그리려면 전체 경기가 필요 → 변경 1건마다 전체 재조회
        ↓
경기가 쌓일수록 제곱으로 무거워짐
```

RP 정확성은 전체 재조회가 아니라 **서버의 영수증 시스템**이 보장한다
(경기 행에 `rp_delta_*` 저장 → 롤백은 그 값을 역산 → `recompute_league_rp`가 최종 정합).
전체 재조회가 지키던 것은 표시용 통계(승/패/연승/최근5경기)와 호칭 계산 입력뿐이다.

C 작업(`2026-08-25_win_count_maintain.sql`)으로 승패 집계는 서버가 유지하게 됐다.

## 선행 완료 작업

| | 내용 | 상태 |
|---|---|---|
| A | 실시간 재조회 디바운스 (400ms) | 배포 완료 |
| C | `win_count`/`lose_count` 서버 유지 + 백필 | 배포 + SQL 적용 완료 |
| — | 공개 순위표 실시간 구독 → 30초 폴링 | 배포 완료 |

## 폐기된 대안

- **D (경기 조회 범위 제한)** — 이력을 잘라내면 리벤지 판정과 호칭이 틀린다.
  잘못된 보너스가 delta로 **영구 저장**되므로 표시 오류보다 나쁘다. 폐기.
- **E (서버 집계 RPC)** — 호칭 로직을 SQL로 이식해야 해서 위험 대비 이득이 적다. 보류.

## 개발 없이 얻는 완화책

**시즌을 학기별로 나눠 운영**하면 경기 수가 0부터 다시 쌓여 제곱 증가가 리셋된다.
이미 시즌 기능이 있으므로 추가 개발이 필요 없고, 학교 운영 흐름과도 맞는다.

## 착수 판단

급하지 않다. A 적용으로 이미 4배 줄었고, 학교로 본격 확장하기 전까지는 버틴다.
**Supabase 실제 사용량을 한두 주 관찰한 뒤** 착수 여부를 정하는 것을 권한다.
추정치는 계산이고, 실측이 훨씬 정확하다.
