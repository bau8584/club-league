# 테스트 — 확인 비용을 줄이는 계획

> 상태: **방침 합의 + 우선순위 1(하이라이트 계산기) 완료. 2(RP·티어)는 미착수**
> 정리: 2026-09-10

이 문서는 "테스트를 몇 % 채우자"는 이야기가 아니다. **무언가를 고친 뒤 그게 맞는지
확인하는 데 드는 비용**을 줄이는 것이 목적이고, 그래서 **무엇을 테스트하지 않을지**를
같이 정한다.

## 왜 하는가

(이 절은 시작할 때의 상황이다. 하이라이트 계산기는 이제 여기서 벗어났다.)

규칙이 맞게 동작하는지 확인하는 유일한 방법이 **화면을 눈으로 보는 것**이었다.

반 필터 하나를 확인하는 데 실제로 든 절차:

1. 브라우저를 연다
2. 로비 → 학교 로비 → 리그 입장 → 하이라이트 탭
3. 스크린샷을 찍는다
4. 데이터가 오래돼서 새로고침한다
5. 다시 찍는다

한 번 확인에 왕복 대여섯 번이고, 스크린샷 한 장이 텍스트 수천 자보다 비싸다.
사람이 하든 AI가 하든 같은 비용이 든다.

더 나쁜 것은 **만들 수 없는 상황이 있다는 점**이다. 2단계에서 정한 규칙 중에는
"동점자가 셋 이상이면 카드 대신 목록으로 내린다"가 있는데, 이걸 화면에서 확인하려면
**동점자가 셋인 날이 실제로 오기를 기다려야 한다.** 기다릴 수 없으니 확인을 안 하게 되고,
확인 안 한 규칙은 반년 뒤에 조용히 깨져 있다.

계산이 화면과 분리되고 테스트가 붙으면 이 전부가 명령 한 줄이 된다.

```
bun test
→ 66 pass, 0 fail  (130ms)
```

가짜 경기 데이터로 "동점자가 셋인 날"을 지어내면 된다.

## 현황

**러너는 `bun test`다.** `package.json`의 `scripts`에도 올라가 있어서 `npm test`로도 돈다.

- 테스트 파일 3개, 케이스 66개, 전부 통과, **약 130ms**
  - `src/domain/highlight-calculator.test.ts` — 37케이스
  - `src/domain/assignment-calculator.test.ts`
  - `src/domain/assignment-rows.test.ts`
- `bun:test`를 쓴다. 별도 설정 파일 없음. `@types/bun`만 devDependencies에 있다.
- 테스트가 붙은 파일은 **전부 `src/domain/`** 에 있다. `src/lib/`에는 하나도 없다.

## 무엇을 테스트하는가

**순수 계산만.** 입력을 주면 출력이 나오고, 그게 전부인 것들.

| 테스트한다 | 테스트하지 않는다 |
|---|---|
| 상 배정 규칙 | 화면이 예쁘게 나오는지 |
| RP · 티어 계산 | 서버 통신, 실시간 갱신 |
| 대진 배정 | 로그인, 권한 |
| 날짜 · 반 묶기 | 브라우저 동작 |

아래 칸을 테스트하려면 가짜 서버와 가짜 브라우저를 세워야 하는데, **그 유지 비용이
얻는 것보다 크다.** 1인 개발 프로젝트에서 감당할 물건이 아니다.

경계는 단순하다. **`src/domain/`은 테스트한다. 나머지는 안 한다.**
그래서 새 계산을 `src/domain/`에 두느냐 `src/lib/`에 두느냐가 곧
"검증할 수 있느냐"의 결정이 된다.

## 브라우저는 여전히 필요하다

테스트가 대체하지 못하는 것이 있다. 정직하게 적어둔다.

- 칩이 흐리게 보이는지, 글자가 잘리는지
- 다크 모드에서 읽히는지
- 실제 리그 데이터에서 이상한 이름이 튀어나오는지
- 실시간 갱신이 도는지

**규칙은 테스트로, 모양은 눈으로.** 둘을 섞지 않는다.
지금은 규칙까지 눈으로 보고 있어서 비싼 것이다.

## 우선순위

### 1. 하이라이트 계산기 — 처음부터 테스트와 함께 ✅ 완료

`src/domain/highlight-calculator.ts` (→ `docs/PLAN-highlight.md`).
**나중에 붙이는 게 아니라 같이 만들었다.** 계획한 케이스는 전부 통과하고, 만들면서
필요해진 것들이 더 붙었다.

**동점과 배정** ✅
- 2연승이 여러 명이면 카드가 아니라 목록으로 내려간다
- 동점자가 둘이면 타이브레이커로 한 명을 고른다 (+ 출전 수까지 같으면 학년·반·번호 순)
- 같은 입력을 두 번 넣으면 항상 같은 결과가 나온다 (배열을 뒤집어도 같다)
- 한 학생이 여러 상의 최댓값이어도 카드는 하나만 받는다
- 드문 상이 흔한 상보다 먼저 배정된다
- `최다승`은 배정 대상이 아니다 (사실이 유일해야 한다)

**상대값 기준** ✅
- 2점제 경기(2:0, 2:1)에서 압승과 접전이 갈린다
- 21점제 경기(21:9, 15:13)에서도 같은 코드로 갈린다
- 그 날 최대 연승이 2면 `연승왕` 카드가 나오지 않는다
- 경기가 1건뿐인 날에 상이 억지로 만들어지지 않는다 (+ 점수차가 전부 같은 날)

**종목** ✅
- 복식이 없는 날 `복식 짝꿍`이 나오지 않는다 (+ 있는 날 짝꿍이 나온다)
- 단식과 복식이 섞인 날 승수가 합산된다

**경계값** ✅
- 그 날 경기가 0건이면 빈 결과를 돌려준다
- 삭제된 학생이 낀 경기에서 터지지 않는다
- 반 정보가 없는 명단(전원 `null`)에서 동작한다

**나중에 붙은 것** — 계획에 없었지만 실제 데이터를 보고 생긴 규칙들
- 해당자가 여섯을 넘으면 목록으로도 내지 않는다 (경계 6/7을 둘 다 고정)
- 하루 한두 경기에서도 갈리는 축: 이변은 RP 차로, 강한 상대는 상대 평균 RP로
- 이변의 크기는 경기 전 RP로 잰다 (경기 후 값을 쓰면 격차가 저절로 깎인다)
- 지난 기록이 없으면 `친구 넓히기`·`첫 승`·`리그 데뷔`를 아예 내지 않는다
- 나빠진 학생은 내지 않는다
- 명경기는 접전 중 총득점 최대, 반대항은 한 반 대 한 반일 때만 센다

이 목록이 "동점자가 셋인 날이 실제로 오기를 기다린다"를 대체했다. 가짜 경기로
27명이 뛴 날도, 일곱 명이 데뷔한 날도 지어낼 수 있다.

### 2. RP · 티어 계산

`src/domain/match-calculator.ts`. **이 앱에서 가장 중요하고 가장 검증이 안 되는 부분이다.**
학생 526명의 점수가 걸려 있는데 지금은 눈으로만 확인한다.

급하지 않지만 목록에는 둔다. 계산의 일부가 `league-store.ts` 쪽에 걸쳐 있어서,
먼저 순수한 부분을 가려내는 작업이 필요하다 (→ `docs/PLAN-store-slimming.md`가 생기면
거기로).

### 3. 기존 두 파일은 유지

배정 계산기 테스트는 이미 잘 돌고 있다. 배정 규칙을 고칠 때 같이 고친다.

## 쓰는 법

기존 파일의 방식을 그대로 따른다. 새로 정할 것이 없다.

```ts
import { describe, expect, it } from "bun:test";
import { buildAssignedMatchRows } from "./assignment-rows";

describe("buildAssignedMatchRows", () => {
  it("팀을 슬롯으로 펴고, 팀 미정 필드(player_ids)는 비운다", () => {
    ...
  });
});
```

**케이스 이름은 한글 문장으로, 규칙 하나에 케이스 하나.**
이름만 훑어도 "이 계산기가 무슨 규칙을 지키는지" 목록이 되도록 쓴다.
반년 뒤에는 이 목록이 설계 문서보다 정확하다 — 문서는 낡아도 테스트는 낡으면 실패한다.

## 하지 않을 것

| | 이유 |
|---|---|
| 커버리지 목표(%) 세우기 | 숫자를 채우려고 의미 없는 테스트를 쓰게 된다 |
| 화면 컴포넌트 테스트 | 가짜 브라우저 유지 비용 > 얻는 것 |
| `league-store.ts` 테스트 | React 훅 + 서버 통신이 얽혀 있다. 계산을 먼저 빼내야 한다 |
| E2E (브라우저 자동화) | 1인 프로젝트에서 유지 못 한다 |
| CI 구축 | 지금은 `bun test` 한 줄로 충분하다 |

## 정리

- 목적은 커버리지가 아니라 **확인 비용**이다
- 경계는 `src/domain/` 하나뿐이다 — 안이면 테스트, 밖이면 안 함
- 새 계산은 **처음부터** 테스트와 함께 만든다. 나중에 붙이지 않는다
- 규칙은 테스트로, 모양은 눈으로
- 다음 할 일: RP · 티어 계산(`match-calculator.ts`). 먼저 `league-store.ts`에 걸쳐 있는
  부분에서 순수한 계산을 가려내야 한다

### 실제로 든 효과

하이라이트 규칙을 열 번 가까이 고치는 동안 브라우저를 한 번도 거치지 않았다.
이름을 다섯 개 바꾸고, 상 하나의 축을 횟수에서 RP 차로 갈아엎고, 목록 상한을 새로
넣는 동안 깨진 것은 **테스트가 먼저 말해 줬다**(이름 변경 때 4건, 축 변경 때 1건).

다만 예상대로 안 되는 것도 확인됐다. 로그인 벽 뒤의 화면은 여전히 사람이 봐야 하고,
"21명이 목록에 뜬다"처럼 **실제 데이터의 모양이 만든 문제**는 테스트가 잡지 못했다.
그건 화면을 보고 알았고, 그다음에야 테스트로 고정했다. 순서가 그렇다.
