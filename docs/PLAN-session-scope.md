# 세션 범위 — 한 리그 안의 여러 수업

> 상태: **설계 합의, 미착수**
> 배정 세션이 리그당 하나뿐이라, 한 리그를 여러 담임이 나눠 쓰는 순간 서로의 수업을
> 지운다. 담임 배포 전에 정리해야 한다. 이 문서는 세션의 소유자를 정하고,
> 그 위에 얹히는 대진 고유번호와 공개 대기열까지 함께 다룬다.

## 왜 하는가

`assignment_sessions`는 **리그당 1행**이다(`league_id = PK`, [league-types.ts:75](../src/lib/league-types.ts)).
그런데 학교 리그 하나가 20개 반을 담는다. 반마다 수업 시간이 다르니
**한 리그 안에 서로 무관한 수업이 여럿** 돌아간다.

지금은 그 여럿이 세션 하나를 공유한다. 결과는 두 가지다.

**하나 — 큐가 통째로 날아간다.** `startAssignmentSession`이 `apiClearQueue`로 리그 전체
큐를 비운다([league-store.ts:2984](../src/lib/league-store.ts)). 5-7 담임이 수업을 시작하면
옆 반에서 진행 중이던 대기열이 사라진다. 지운 쪽도 지워진 쪽도 알아채지 못한다.

**둘 — 학생이 남의 반 대진을 본다.** 세션이 하나뿐이니 큐도 하나다. 5-5 학생이 자기
폰을 열면 6교시 5-7의 대진이 떠 있다. **이건 순차 수업에서도 이미 그렇다.**

### 배포 모델이 이걸 예외가 아니라 정상 경로로 만든다

초대 링크(`/join?classId=...`)는 **공동 관리자 권한**을 준다
([InviteDialog.tsx:19](../src/components/league/InviteDialog.tsx)). 담임들에게 앱을 뿌리면
각자 리그를 만드는 게 아니라 **하나의 리그를 함께 쓴다.**

즉 "두 반이 동시에 수업하는 일"은 드문 사고가 아니라 배포와 동시에 기본 상황이 된다.

## 결정 — 세션의 소유자는 리그 타입이 정한다

| | 세션 단위 | 소유자 |
|---|---|---|
| **학교** | 교사 한 명당 하나 | 교사 계정 |
| **동호회** | 리그당 하나 (지금 그대로) | 없음 |

리그와 모임의 관계가 반대이기 때문이다.

- 학교 리그는 **여러 개의 독립된 모임**을 담는다 → 모임마다 세션.
- 동호회 리그는 **하나의 모임 그 자체**다 → 리그당 세션 하나가 맞다.

동호회에 교사별 분리를 적용하면 오히려 망가진다. 운영진이 둘인 동호회에서 각자 앱을
열면 세션이 갈리고, 같은 사람들이 양쪽 큐에 배정된다. 학교에서 예외적 실패인 것이
동호회에서는 정상 상황이다.

이 코드베이스는 이미 `leagueType`으로 곳곳에서 갈린다(배정 프리셋 기본값 등). 새 축이
아니라 있는 축에 얹는다.

### 스키마

```
assignment_sessions
  id          (신규 PK, surrogate)
  league_id
  owner_id    (신규, nullable — 학교만 채운다)
  player_ids, match_type, started_at, updated_at   … 그대로
  next_seq    (신규 — 아래 "대진 고유번호" 참조)

  UNIQUE (league_id, owner_id)

scheduled_matches
  session_id  (신규)
```

`owner_id`를 PK에 직접 넣지 않는다. Postgres에서 NULL은 서로 같지 않게 취급되어
동호회 행(`owner_id IS NULL`)의 유일성이 보장되지 않는다. **PK는 별도 id, 유일성은
부분 인덱스로** 건다.

동호회는 `owner_id`가 비어 있는 채로 지금 동작을 그대로 유지한다. **마이그레이션
영향이 사실상 없다.**

## 무엇을 만들지 않는가

### 반 조합을 세션 키로 쓰기 — 폐기

고른 반 목록(`{5-5}`, `{5-5,5-7}`)을 키로 삼는 안. UI가 하나도 안 늘어난다는 장점이
있었으나 두 가지로 깨진다.

- **키가 조작에서 파생된다.** 반 칩을 잘못 누르면 조용히 다른 세션으로 넘어간다.
  화면에는 반이 바뀐 것처럼만 보이고, 큐가 왜 비었는지 알 방법이 없다.
- **학년 대전과 겹친다.** `{5-5,5-7}` 세션이 도는 중에 누가 `{5-5}`를 열면 다른
  키인데 학생이 겹친다.

### 방 기반 — 보류 (폐기는 아님)

"이미 도는 세션이 있으면 참여할지 새로 팔지 고르게 한다"는 안. 항상 묻는 게 아니라
충돌할 때만 묻는 것이라 부담이 크지는 않다. 그래도 지금은 아니다.

- **잘못 고를 수 있는 물음을 새로 만든다.** `5학년 체육 (13:18 시작) — 참여할까요?`를
  봤을 때 그게 옆 반 수업인지 내가 어제 안 닫은 세션인지 구분할 근거가 화면에 없다.
  잘못 참여하면 남의 큐에 내 아이들을 밀어 넣는다.
- **확장 경로가 한쪽으로만 열려 있다.** 아이디 기반 → 방 기반은 세션에 참여자 목록을
  덧붙이는 일이고, 기존 세션은 "참여자가 소유자 한 명인 방"으로 그대로 해석된다.
  반대 방향은 UI를 걷어내고 만들어진 방을 정리해야 한다. **같은 목적지인데 한쪽이 더
  작은 걸음이다.**

필요해지는 경우는 하나뿐이다 — **팀티칭**. 두 교사가 각자 계정으로 한 큐를 함께 몰아야
할 때. 실제로 걸리면 그때 얹는다. 신호는 분명할 것이다: 같은 아이들로 각자 세션을 열어
대진이 겹치는 일이 생긴다.

### 코트 수 설정 — 폐기

상위 N줄을 "뛰는 중"으로 표시하기 위해 코트 수를 받는 안. 체육관마다 다르고, 값이
실제와 어긋나면 화면이 거짓말을 한다. **대진 고유번호가 같은 문제를 코트 수를 모른 채
푼다**(아래).

### `status: "called"`로 뛰는 중 판정하기 — 폐기

스토어에 `callScheduledMatch`(waiting → called + 입장 푸시)가 이미 있으나 아무도 호출하지
않는다. 이걸 살리면 코트 수를 몰라도 뛰는 중인 경기가 저절로 정해진다.

그러나 **경기 시작마다 탭이 하나 늘어난다.** 26명 데리고 4코트 돌리는 교사는 이걸 매번
누르지 않는다. 안 누르면 화면이 "뛰는 중 0개"라고 거짓말한다. **지켜지지 않을 규율에
정확성을 거는 설계**다.

### 반대항전 — 범위 밖

이 기능이 품지 않는다. 일상 수업의 목표는 `전원이 한 판씩`이라 배정 엔진이 개인 단위
커버리지를 최적화한다. 반대항전의 목표는 `어느 반이 이겼나`로 팀 단위다.
`calculateAssignment`가 답할 수 있는 질문이 아니다.

나중에 독립 기능으로 만든다. 명단·경기 기록·푸시 배관은 재사용하고, **배정 엔진과 순위
계산은 새로 짠다.** 지금 이를 위해 남겨둘 것은 없다 — 배관은 이미 반 정보를 들고 있다.

반대항전을 범위에서 빼면 **세션 간 학생 겹침이 구조적으로 사라진다**(반 단위이므로).
따라서 다음 두 가지도 불필요해진다.

- `fillAssignmentQueue`의 `queuedIds`를 세션 범위를 넘어 전역으로 유지하는 특례
- 동시 채우기 레이스를 막기 위한 서버 함수

세션마다 교사가 한 명이면 두 장치 모두 성립할 상황이 없다.

## 함께 해야 하는 것

### 1. 공개 대기열 링크

**보여주는 기기와 조작하는 기기를 분리한다.**

지금 아이들이 몰려와 보는 태블릿은 교사 계정으로 로그인돼 있다. 아이 누구나 대기열의
`×`를 눌러 대진을 지울 수 있고 확인창도 없다. 명단 관리·경기 삭제·리그 설정까지
열려 있다. **세션 설계와 무관하게 지금 이미 있는 위험이다.**

`__root.tsx`에 `PUBLIC_PATH_PREFIXES = ["/ranking/"]`로 로그인 없는 공개 경로 패턴이
이미 있다([__root.tsx:173](../src/routes/__root.tsx)). 대기열도 같은 방식으로 연다.
버튼이 없으니 아이가 만져도 아무 일도 일어나지 않는다.

**주소는 세션이 아니라 소유자를 가리켜야 한다.**

```
학교    /queue/{classId}/{ownerId}
동호회  /queue/{classId}
```

세션 id를 가리키면 수업마다 주소가 바뀌어 태블릿을 매번 다시 연결해야 한다. 소유자를
가리키면 **한 번 띄워두고 그 교사가 지금 돌리는 세션을 계속 따라간다.** 한 번 설정하고
잊는 물건이 된다.

이로써 아이디 기반의 유일한 실질적 불편("여러 기기를 쓰려면 계정을 공유해야 한다")이
사라진다. 조작 기기는 하나면 충분하고 나머지는 보기 전용이다.

### 2. 대진 고유번호

지금 줄 번호는 배열 인덱스다([MatchQueue.tsx](../src/components/league/MatchQueue.tsx)의
`orderMark(i)`). 1번이 끝나면 아래가 전부 밀려 올라간다. **번호를 기억하는 것이
무의미하다** — "너희 5번째야"라고 알려줘도 몇 분 뒤엔 3번째다. 아이는 매번 처음부터
훑어야 하고, 교사가 "7번!" 하고 부르는 것도 불가능하다.

고정 번호로 바꾼다. 1번이 끝나도 2번은 2번으로 남는다.

**코트 수를 몰라도 되는 게 핵심이다.** 아이가 "우리 7번"을 기억하면 그만이고, 2코트든
4코트든 상관없다. 앞서 폐기한 코트 수 설정과 `called` 판정이 풀려던 문제를 이쪽이
더 싸게 푼다.

구현:

- `next_seq`를 세션 행에 둔다. `startAssignmentSession`이 세션을 새로 쓰므로 **수업이
  바뀌면 번호가 자연히 1번부터** 다시 시작한다. 초기화 로직이 따로 필요 없다.
- **발급은 반드시 원자적으로.** `UPDATE ... SET next_seq = next_seq + n RETURNING`을
  RPC로 감싼다. 클라이언트에서 읽고-더하고-쓰면 폰과 태블릿이 같은 값을 읽어
  `#7`이 두 개 생긴다. 번호가 아이들이 부르는 이름이 된 뒤에 고치려면 이미 나간
  번호를 어떻게 할지 곤란해진다.
- **정렬 기준을 `created_at`에서 `seq`로.** 지금은 `baseTimeMs`가 만든 타임스탬프로
  정렬하는데, 기기 시계가 다르면 순서가 흔들린다.
- `orderMark`는 버린다. `①②③`은 20까지만 원문자고 그 뒤는 `21.`로 떨어진다. 고정
  번호는 한 수업에 쉽게 20을 넘는다. `#7` 배지로 바꾼다.
- **빈 번호는 그대로 둔다.** 1·3·5가 끝나면 `#2 #4 #6 #7`이 남는다. 은행 번호표와 같은
  모양이고, 빈자리가 곧 진행 상황이라 정보가 된다. 고칠 것이 아니다.

번호가 "언제"를 답하지 않게 되는데, 그 답은 이미 다른 데 있다. 헤더의
`내 차례 N번째예요`가 위치를 계산한다. **줄의 번호는 "어느 게 우리 것", 개인 문구는
"얼마나 남았나"** 로 역할을 나눈다. 지금은 하나가 두 일을 겸하다 둘 다 못 하고 있다.

### 3. 큐 줄 조작 (독립)

세션 범위와 무관하다. 아무 때나 끼워 넣을 수 있다.

- **행 전체를 결과 입력 버튼으로.** 지금 `결과 입력`은 `h-7`(28px), `×`는 약 24px로
  둘 다 권장치 44px에 한참 못 미친다. 그런데 **행 자체는 이미 약 48px다** — 알맞은
  타깃이 이미 있는데 눌리지 않을 뿐이다. 사람들이 이름을 누르는 건 실수가 아니다.
  잘못 눌러도 폼이 열릴 뿐이라 되돌리는 비용이 0이다.
  `결과 입력` 글자는 버튼이 아닌 텍스트로 남겨 무엇이 일어날지 알린다.
- **`×`를 키우고 확인을 붙인다.** 행이 큰 타깃이 되면 `×`와 붙는다. 지금
  `removeScheduledMatch`는 확인 없이 즉시 삭제한다. `MatchesTab`의 `confirmCancel`
  팝업 패턴을 쓴다. **되돌릴 수 없는 동작만 조준을 요구하고, 되돌릴 수 있는 동작은
  아무 데나 눌러도 되게** — 지금은 정확히 반대다.

`×`가 "취소"가 아니라 "끝났음"으로 쓰이는 건 그대로 둔다. 결과를 아래 카드로 바로
입력하거나, 줄에서 시작했어도 선수를 교체하면 `sameMatch` 가드에 걸려 줄이 남기
때문이다([MatchesTab.tsx:304](../src/components/league/MatchesTab.tsx)). 통계의 진실은
`matches` 테이블이지 큐가 아니므로 취소와 완료를 구분할 실익이 없다.

## 손대는 곳

| 파일 | 내용 |
|---|---|
| 마이그레이션 | `assignment_sessions` PK·`owner_id`·`next_seq`, `scheduled_matches.session_id` |
| `services/league-api.ts` | `apiClearQueue`·`apiFetchScheduledMatches`를 세션 범위로, `next_seq` RPC |
| `lib/league-store.ts` | `loadAssignmentSession`을 소유자로 조회, `fillAssignmentQueue`에서 seq 발급 |
| `lib/league-store.ts` 실시간 | 구독은 `league_id` 필터 그대로. 수신 후 **세션으로 걸러야** 한다 |
| `components/league/MatchQueue.tsx` | `seq` 배지, 정렬 기준, 행 클릭, `×` |
| `routes/queue.*.tsx` (신규) | 공개 대기열. `__root.tsx`의 `PUBLIC_PATH_PREFIXES`에 추가 |

`fillAssignmentQueue`의 후보 산정은 이미 세션의 `player_ids`를 쓰므로 손댈 것이 거의 없다.

## 순서

1. **세션 범위** — 나머지가 전부 이 위에 얹힌다
2. **공개 대기열 링크** — 1과 함께. 세션의 주소 체계를 정하는 일이 곧 링크 주소를 정하는 일이다
3. **대진 고유번호 + `next_seq` 원자화** — 1 이후
4. **행 클릭 · `×`** — 독립, 아무 때나

**세션 범위는 담임 배포 전에 끝내야 한다.** 뿌린 뒤에 고치면 이미 돌아가는 수업
데이터를 옮겨야 하고, 그 사이 선생님들이 서로 큐를 지우는 걸 겪는다.

## 나중에 판단할 것

## 검증

컴포넌트 테스트가 없다(`src`에 `*.test.tsx` 없음). 도메인 테스트만 있으므로
아래는 손으로 확인한다.

1. 교사 A가 5-5로 수업 시작 → 대진 채움. 교사 B가 **다른 계정으로** 5-7 수업 시작
   → **A의 큐가 그대로 남아 있어야 한다**
2. A의 화면에 B의 대진이 보이지 않아야 한다. 그 반대도
3. 5-5 학생 계정 → 5-5 큐만 보인다
4. 동호회 리그 → 지금과 완전히 동일하게 동작 (회귀 확인)
5. `#7`이 끝나도 `#8`은 `#8`로 남는다. 새 수업을 시작하면 `#1`부터
6. 같은 계정으로 폰과 태블릿에서 동시에 채우기 → 번호가 겹치지 않는다
7. 공개 링크를 로그아웃 상태로 열기 → 목록만 보이고 버튼이 없다.
   수업을 새로 시작해도 **같은 주소가 계속 따라간다**
8. 줄을 아무 데나 눌러 결과 입력으로 간다. `×`는 확인을 거친다
